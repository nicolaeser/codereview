# Presentation contract

## Scope and authority

This repository has no owned web UI, frontend framework, component library, theme, design tokens, CSS, assets, viewport contract, or client-side interaction layer. GitLab owns the rendering of service-produced Markdown; GitLab and GitHub own the visual theme, typography, responsive behavior, and focus treatment of the Markdown surfaces they host.

This contract applies when changing:

- GitLab notes, inline discussions, merge-request summaries, help, configuration, ask replies, progress, or failure output;
- operator-facing structured logs; or
- repository Markdown documentation.

The implementation sources of truth are `internal/review/format.go`, `internal/review/commands.go`, the user-visible strings in `internal/review/service.go`, and `internal/logx/logx.go`. Configuration behavior is authoritative in `internal/config/config.go`; `README.md` and `docs/CONFIGURATION.md` describe the public contract. For implementation rules, load [service engineering](instructions/service-engineering.md). When untrusted content, prompt boundaries, or publication behavior changes, also load [review trust boundaries](knowledge/review-trust-boundaries.md). Use the [review-pipeline playbook](playbooks/change-review-pipeline.md) for a material end-to-end change.

## Presentation principles

- Output must remain concise, scannable, and useful without custom styling.
- The primary result and required action must remain visible; secondary file, issue, limit, technical, and suggestion details may be disclosed with `<details>`.
- `compact` is the default comment style. `detailed` may expose more metadata and longer content, but must preserve the same meaning and state coverage.
- User-authored merge-request text must be preserved when CodeReview updates its marker-delimited summary.
- Model-generated review findings and walkthroughs must retain their explicit human-verification disclosure; ask replies must retain their AI-generated product label. References such as “AI-generated” and “Generated by CodeReview” are legitimate product-domain labels, not repository-work attribution.

## Markdown hierarchy and density

- Generated output must use semantic Markdown headings in order: `##` for a CodeReview surface and `###` for its visible sections.
- Block elements must be separated with blank lines. Narrative content should use paragraphs or short lists; tables should be reserved for repeated, comparable fields.
- Paths, identifiers, commands, modes, configuration values, and issue references should use backticks where the current formatter does so.
- The summary and result must remain outside collapsed regions. Wide or optional detail must not be the only place where a failure, severity, or required action is stated.
- Dynamic table cells must use the existing `escapeTable` helper. Fields that the formatter defines as bounded inline summaries must continue to use `truncateInline` at their current bounds. These helpers protect layout; they must not be described as general sanitization.
- Preserve the established bounds for titles, bodies, summaries, walkthrough entries, issue assessments, and suggestions unless the product contract is intentionally changed and validated in both styles.

GitLab controls containers, alignment, wrapping, and narrow-screen behavior. Generated output must not add inline CSS, fixed widths, viewport assumptions, or layout HTML to compensate for renderer behavior.

## Surfaces, components, and states

Changes must reuse the existing composition points instead of assembling parallel formats:

- `FormatFinding` for inline findings and committable suggestions;
- `FormatWalkthrough` for review summaries, results, changed files, linked issues, notices, and technical details;
- `UpdateDescription` for the CodeReview-owned merge-request summary block;
- `HelpMarkdown` and `configurationMarkdown` for command and configuration discovery; and
- the existing service messages for processing, failure, ask, summary-only, and resolution states.

Status must never depend on color or emoji alone. Keep a textual state or severity alongside any icon. Loading, empty/no-finding, success, warning/finding, and failure output must say what occurred and expose the next useful action when one exists.

The repository owns no forms, disabled or selected controls, hover or pressed styling, touch targets, or keyboard shortcuts. The only current interactive disclosure is GitLab-rendered `<details>`/`<summary>`; GitLab owns its focus, keyboard, and touch behavior.

Committable replacements must remain in a `suggestion` fence inside the established disclosure and must satisfy the formatter's size and nested-fence guards. The `codereview-summary` comment markers are control data, not decoration; changing them requires preserving idempotent replacement and surrounding user text.

## Accessibility and decorative treatment

- Headings, table headers, disclosure labels, and state text must remain meaningful when emoji and visual styling are unavailable.
- The sole explanation of an error or finding must not be hidden in a collapsed region.
- Icons may be used only as redundant semantic cues; generated output must not add decorative emoji, gradients, shadows, borders, or color conventions that the repository cannot control.
- The repository defines no motion or transition behavior. Generated Markdown must not introduce animation or scripts; reduced-motion behavior remains the host renderer's responsibility.
- Raw HTML must remain limited to the established `<details>`, `<summary>`, `<sub>`, and summary-marker comments. New HTML may be added only with verified GitLab support and a concrete semantic need that Markdown cannot meet.

## Structured logs

Logs are newline-delimited JSON, not prose UI. Changes must preserve the UTC RFC 3339-nanosecond `time`, lowercase `level`, and concise `message` fields emitted by `internal/logx/logx.go`; variable context must use structured key/value fields. Log messages must not contain Markdown, ANSI color, emoji, or multi-line decoration. Security and privacy requirements for log content are authoritative in [security and privacy](instructions/security-privacy.md).

## Repository documentation

- Documentation must use concise professional English, semantic headings, relative Markdown links, fenced code blocks with language identifiers, and code spans for literal technical values.
- Tables should be reserved for stable comparisons or exact mappings; prose and short lists should carry procedures and explanation.
- Documentation must not copy large configuration inventories or source snippets when a link to the canonical file is more reliable.
- Diagrams may clarify a real multi-step relationship, but one existing Mermaid diagram does not establish a requirement to diagram routine changes.

## Prohibited patterns and exceptions

- Work must not invent a visual design system, theme behavior, breakpoints, typography scale, component variants, or motion language for this backend-only repository.
- Changes must not create duplicate output formatters or hand-build an existing surface at a new call site.
- Essential outcomes must not move into closed disclosures merely to reduce comment length.
- Product AI disclosures must not be removed under the repository-work attribution rule.
- GitLab renderer behavior or escaping must not be treated as proven without verification. An unverified host-renderer assumption must be recorded explicitly.
- Existing supported HTML and emoji are narrow compatibility exceptions; they do not authorize arbitrary HTML or decorative output.

## Verification

For user-visible output changes:

1. Exercise every affected surface and the relevant present, absent, empty, long, and special-character inputs.
2. Verify `compact` and `detailed` behavior, findings and no-findings results, optional disclosures, suggestion fences, and summary replacement when applicable.
3. Confirm primary meaning remains clear without emoji and without opening secondary disclosures.
4. Run `go test ./internal/review` and then the repository checks required by [service engineering](instructions/service-engineering.md).
5. Inspect representative rendered GitLab Markdown when the change relies on host rendering; if that environment is unavailable, report the assumption and residual risk.

For log changes, decode representative output as JSON and confirm the stable fields and one-record-per-line shape. For documentation-only changes, verify internal links and run `git diff --check`.
